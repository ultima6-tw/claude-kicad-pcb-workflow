# How we design a PCB with Claude Code and KiCad

> **Status: workflow demonstration, NOT a verified design.**
> The example board in this repo has never been fabricated or powered on.
> Its layout is unfinished: signal routing for one of four cells is done, but power and ground planes are still in progress.
> Do not send these files to a fab, and do not reuse the circuit without your own review.
>
> **High-voltage warning:** the example design floats on a +300 V platform and uses ±52 V rails.
> If you build anything similar, follow proper isolation, creepage and safety practices. The DRC rules here only check clearance, not creepage.

This repo documents the whole process we used to design a PCB with an AI assistant (Claude Code), from datasheets to Gerber files.

The example is a 16-channel high-voltage arbitrary waveform generator: four FPGA modules (Trenz TE0720), each driving four AD8460 DACs, with isolated power on one 300 × 290 mm, 6-layer board.

The main idea: **the AI handles the schematic the way it handles code.** Connections are written as text, repeated structure is generated by scripts, and every step is checked by a program. Then KiCad turns the result into a board.

## The process

```
 1. Setup            KiCad 10 + KiCad MCP server + Claude Code
 2. Datasheets       every connection traced to a datasheet section
 3. Parts            built-in → vendor (with fixes) → generated from datasheet
 4. Sub-circuits     parts + net labels on pins, no wires          → ERC
 5. Hierarchy        generated by script                           → pin-by-pin check
 6. Into the board   kicad-cli netlist written into pads           → schematic parity
 7. Design rules     net classes + high-voltage clearance          → negative test
 8. Placement        script (or KiCad GUI)
 9. Routing          script (or KiCad GUI)                         → DRC
10. Output           Gerber, drill, BOM, position files
```

### 1. Setup
KiCad 10.0.6, [mixelpixx/KiCAD-MCP-Server](https://github.com/mixelpixx/KiCAD-MCP-Server), and Claude Code on macOS. Install steps and common problems are in [`docs/kicad-mcp-setup.md`](docs/kicad-mcp-setup.md).

We first ran a tiny LED + resistor board through the full flow (schematic → ERC → PCB → DRC → Gerber) to make sure the tool chain works before starting real work.

### 2. Read the datasheets first
Before drawing anything, Claude reads the datasheets and application notes and writes down where each connection comes from (for example, "AD8460 datasheet, Figure 58"). If a choice has no reference, it is labelled **"no reference, design decision"**, so a reviewer knows what to double-check. These notes are kept next to the design as a running log.

### 3. Parts
In this order:
1. **KiCad built-in libraries** where possible.
2. **Vendor libraries** (Ultra Librarian), imported by a script that also fixes their errors. We found wrong pin types, an exposed pad with no matching symbol pin, and one part with the wrong package.
3. **Generated from the datasheet** when nothing exists. For example, `gen_te0720.py` reads connector pins from the module's schematic PDF. Every dimension is then compared with the official drawing.

### 4. Sub-circuits
Each sub-circuit (one DAC channel, the power stage) is drawn through the MCP server. Parts are placed, and **net labels are put directly on pins instead of drawing wires**. The schematic is then effectively a text netlist that is easy to read, diff and check. ERC runs after each sub-circuit.

### 5. Hierarchy
`build_integrated.py` assembles the full design: root → POWER, CELL ×4 → DAC ×4 (693 parts, 22 sheets). One DAC sheet is reused 16 times, with reference designators offset per instance. `check_integrated.py` then compares every pin against each sub-circuit's netlist, for example all 256 FPGA↔DAC signals.

### 6. Into the board
The MCP command `sync_schematic_to_board` creates the footprints. It could not assign nets in a reused multi-level hierarchy, so `assign_nets.py` writes the `kicad-cli` netlist into the pads. `kicad-cli pcb drc --schematic-parity` confirms that the board matches the schematic (0 issues).

### 7. Design rules
`apply_netclass.py` assigns nets to the isolated side A and the high-voltage side B. A custom rule requires ≥ 2.5 mm between them. `test_hv_rule.py` then places a deliberate violation and checks that DRC catches it. **A rule that has never failed has not been tested.**

### 8–9. Placement and routing
We scripted these to see how far it goes. `place_board.py` places one cell. `route_cell.py` is a grid A* router that routed all 136 signal nets of one cell after three rounds (about 17 minutes). It only finds a path: it does not optimize length or impedance. For most boards, placing and routing in the KiCad GUI is probably the more practical choice.

### 10. Output
Gerber, drill, BOM and position files are exported with `kicad-cli`. This was done for the LED test board and a smaller isolated power board, but not yet for the example board.

## Pitfalls we hit

Each of these failed **silently**: no error, and the checks still looked clean.

- **Net classes vanish → high-voltage rules stop working, DRC still passes.** `pcbnew.LoadBoard` from a folder without a `.kicad_pro`, then `SaveBoard` into a folder that has one, overwrites the project file with defaults.
- **MCP `create_netclass`** reported success but did not write the net assignments to `.kicad_pro`.
- **Hierarchical net names:** the board may say `VIN_FILT` while the schematic says `/VIN_FILT`. Net-class patterns must cover both forms.
- **Zone fill uses whatever project file is next to the board.** Fill with the wrong `.kicad_pro` and the copper ignores your clearance rules.
- **MCP keeps the board in memory.** After a script edits the file, call `reload_board` / `open_project` before using MCP again.
- **After upgrading KiCad, restart the Claude Code session**, or the MCP server keeps using the old `pcbnew`.
- **KiCad DRC caps each violation type at about 200 entries.** Check a copy of the board with only the parts you are working on, or real problems get buried.

## Third-party material

We respect the terms of every source we used. Some files are therefore **not in this repo**, and you need to get them yourself.

**You can open the design without them.** KiCad stores a copy of each symbol and footprint inside the `.kicad_sch` and `.kicad_pcb` files. You only need the items below if you want to re-run the part scripts.

On a fresh clone, ERC reports 10 warnings, `lib_symbol_issues` and `footprint_link_issues`, for the five missing Ultra Librarian libraries. This is expected. There are no other ERC violations.

### Ultra Librarian parts (not included)

Some parts come from [Ultra Librarian](https://www.ultralibrarian.com/). Their agreement allows designs that use these parts to be shared, including as open source, but it does not allow redistributing the part libraries themselves. Download these parts yourself in KiCad format:

| Part | Used for |
|---|---|
| AD8460BSVZ | High-voltage DAC (16×) |
| REF5050IDR | 5 V reference |
| TPS75233QPWPR | 3.3 V LDO |
| REC15E-2405SZ | Isolated 5 V supply |
| R3M-2409S (SMD) | Isolated 9 V supply |

Then run the import scripts. They copy the parts into the project and apply our fixes, which are written in the scripts so you can see what was changed and why:

```bash
python3 tools/import_ul_ad8460.py <your-library>/KICAD/v9 kicad/lib
python3 tools/import_ul_parts.py  <your-library>/KICAD/v9 kicad/lib
```

The symbols and footprints of these parts that are embedded in the design files remain the property of EMA Design Automation (Ultra Librarian) or the manufacturer. They are **not** covered by this repo's license.

### Trenz TE0720 pin table (not included)

`tools/gen_te0720.py` builds the module's connector symbol from a pin table. That table is extracted from the TE0720 schematic, which Trenz Electronic does not allow to be reproduced. To rebuild it, download the TE0720 schematic (Rev 04) from the [Trenz Electronic wiki](https://wiki.trenz-electronic.de/display/PD/TE0720+TRM), then:

```bash
pdftotext -f 5 -l 5 -bbox TE0720-04_schematic.pdf page5.html   # pdftotext is part of poppler
python3 tools/extract_te0720_pins.py page5.html kicad/lib/te0720_pins.json
```

### KiCad libraries

The TE0720 footprint reuses the pad geometry of KiCad's built-in Samtec LSHM footprints. For this reason, `kicad/lib/` is licensed under CC-BY-SA 4.0, the same license as the [KiCad libraries](https://www.kicad.org/libraries/license/). The other parts we made ourselves from datasheets (CQB150W, LMK1C1106A) are in the same folder and use the same license.

### Datasheets

We only link to datasheets and do not include them. Symbols and footprints follow the manufacturers' published data.

## What "verified" means here

The program checks prove that **the wiring matches the design intent**. They do not prove that the design is correct. There was no simulation, no fabrication and no measurement.
